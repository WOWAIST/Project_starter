## 3. Git 워크플로우

### 3.1 브랜치 전략

```
main          ─────────────────────────────────── (항상 배포 가능)
  │
develop       ───────────────────────────────────
  │               │               │
feature/*     ────┘   fix/*   ────┘
```

| 브랜치 | 설명 | 병합 대상 |
|--------|------|---------|
| `main` | 프로덕션 배포본 | - |
| `develop` | 통합 개발 브랜치 | `main` |
| `feature/{{기능}}` | 기능 개발 | `develop` |
| `fix/{{버그}}`  | 버그 수정 | `develop` |
| `hotfix/{{버그}}` | 긴급 수정 | `main` + `develop` |

### 3.2 브랜치 네이밍 규칙
```
feature/{{이슈번호}}-{{짧은-설명}}
fix/{{이슈번호}}-{{짧은-설명}}

예시:
feature/42-user-login
fix/87-token-refresh-error
```

## 4. 커밋 컨벤션

```
<타입>(<범위>): <요약>

[본문 — 선택사항]

[이슈 참조 — 선택사항]
```

### 커밋 타입

| 타입 | 사용 상황 |
|------|---------|
| `feat` | 새로운 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `style` | 코드 포맷팅, 세미콜론 등 (로직 변경 없음) |
| `refactor` | 리팩터링 (기능 변화 없음) |
| `test` | 테스트 추가/수정 |
| `chore` | 빌드, 패키지 설정 등 |

**예시**
```
feat(auth): 소셜 로그인 기능 추가

Google OAuth2를 이용한 소셜 로그인을 구현합니다.

Closes #42
```

## 5. PR (Pull Request) 규칙

### 5.1 PR 기준
- 하나의 PR은 하나의 목적만 가질 것
- PR 단위는 리뷰어가 1시간 내 검토 가능한 크기로 유지
- 최소 **{{n}}명** 이상의 승인 후 머지

### 5.2 PR 템플릿

```markdown
## 변경 사항
<!-- 무엇을 왜 변경했는지 -->

## 스크린샷 (UI 변경 시)
<!-- Before / After -->

## 테스트 방법
<!-- 리뷰어가 직접 테스트할 수 있도록 단계 기술 -->

## 체크리스트
- [ ] 코드 셀프 리뷰 완료
- [ ] 테스트 추가/수정 완료
- [ ] 문서 업데이트 필요 여부 확인
```

### 5.3 코드 리뷰 가이드
- 리뷰는 **{{시간}} 내** 시작하는 것을 원칙으로 함
- 코드가 아닌 사람을 비판하지 않기
- 칭찬도 코멘트로 남기기 (`nit:` 접두어로 사소한 의견 표시)
- `[Required]` / `[Optional]` / `[Question]` 접두어로 코멘트 성격 구분

## 6. 코드 컨벤션

### 6.1 공통
- **들여쓰기**: 스페이스 2칸
- **줄 최대 길이**: {{n}}자
- **Lint**: {{ESLint / Prettier 등}} 설정 따름

### 6.2 네이밍 규칙

| 대상 | 규칙 | 예시 |
|------|------|------|
| 변수/함수 | camelCase | `getUserName` |
| 클래스/컴포넌트 | PascalCase | `UserProfile` |
| 상수 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| 파일 (컴포넌트) | PascalCase | `UserProfile.tsx` |
| 파일 (유틸) | kebab-case | `format-date.ts` |

## 7. 이슈 관리

### 이슈 레이블

| 레이블 | 설명 |
|--------|------|
| `bug` | 버그 리포트 |

| `docs` | 문서 관련 |
| `priority:high` | 높은 우선순위 |
| `priority:low` | 낮은 우선순위 |
